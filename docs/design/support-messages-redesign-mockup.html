The fix

Opening: start on a settled view rather than a guess. The banner's Read already knows you have unread messages, so it should open the sheet on the list — pass the intended view in rather than letting the sheet work it out afterwards. Where it genuinely cannot know (the ☰ row on a cold open), hold the body blank until the fetch answers; the sheet's frame and title can paint immediately, so there is no perceived delay.

Closing: stop resetting the view before the fade. Reset when the sheet next opens, not on the way out, so it disappears as whatever you were looking at.

What each row now answers. A dot and a heavier subject for unread. A one-line preview of the last message, prefixed by who wrote it — so you can tell an answer from your own words without opening it. A relative time. A status chip saying whose move it is, and the category, so a person with several open threads can tell them apart. The reference drops to the end, where it belongs: it matters on a phone call, not while scanning.

Grouped, not just sorted. Waiting on you first, then Open, then Closed — the same whose-move-it-is idea the operator's queue already uses, so both ends of the conversation are organised by the same question.

“New request” is demoted to an outline button and moved under the list. It is still one tap, but it is no longer the loudest thing on the screen. That inversion is the actual fix for duplicate tickets: today the list looks like a receipt and the button looks like the action.

What this needs that we do not already have

Everything except the preview line is already loaded — status, category, `lastMessageAt` and the unread comparison all live on `SupportThread` today. The preview needs the last message's body and author, which means either a small denormalised column updated by the existing touch_support_thread() trigger, or a second query. The trigger already writes on every message, so adding last_message_preview and last_author_kind there is cheap and keeps the list to one round trip.

3 · One more, found while testing

ⓘDismissing the banner is permanent. Pressing ✕ hides it for the session — but it stays hidden even when a new message arrives afterwards, while the ☰ badge keeps counting. Confirmed on device. The dismissal should be remembered against the count it dismissed, so a later message brings the banner back.
