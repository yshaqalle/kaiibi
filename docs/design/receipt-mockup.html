Design notes

Replaces the rounded cream card in buildReceiptHtml() and the native preview in receipt-modal.tsx with an 80mm thermal-tape receipt: monospace throughout, dashed rules, a four-column item table, tabular figures, and a Kaiibi footer.

How the reference maps onto kaiibi's data

  • Tagline / street address / VAT ID — dropped. No tax-id field exists anywhere in kaiibi (not on Shop, not on Location, not in any migration), so the reference's VAT/Tax ID line has nothing to print and is gone for good. The header keeps shop name, branch, city · neighborhood, phone and today's hours.
  • Mobile-money merchant ID — printed under a ZAAD or e-Dahab payment line, and only when that method was used on the sale. A cash-only receipt prints none (variant B).
  • Register — dropped. kaiibi has no register concept; Cashier stays.
  • Item sub-line — the reference uses it for a product description. kaiibi has none, so the slot carries the per-line discount (ReceiptItem.discountCents) instead, which today prints as a whole extra row.
  • Rows the reference has no slot for — Points used (N), foreign-currency payment detail (€27.60 @ 0.92/$ · change €1.30), the CUSTOMER block and Points earned all keep their current fields, restyled to the tape.
  • Return policy — the shop's own returnPolicy string sits where the reference's "Returns accepted within 14 days" line is. Absent when unset (variant B).
  • Logo — respects receiptShowLogo; cashier respects receiptShowCashierName.

Decided

  • QR, not a 1D barcode. It encodes KR- plus sales.id uppercased — 35 characters, all inside QR's alphanumeric charset, which holds the symbol at version 2 (25×25) at ECC-M. Lowercase hex or a colon separator would force byte mode and a bigger symbol, so the case matters. About 16mm square printed at 4 dots/module on a 203dpi head, against a 1D code eating the full tape width. No migration: the uuid already exists, so receipts printed today stay resolvable whenever scan-to-return gets built. ECC-M also recovers ~15% damage, which matters for paper that lives in a pocket. The app's camera scanner already accepts qr (RETAIL_BARCODE_TYPES).
  • The short code under it is a search hint, not a key. 4F2A-0193 is the head of the same uuid, for reading out over the phone or typing into search. Collisions are harmless because it only narrows a list — the QR carries the authoritative id.
  • Merchant IDs live on the location, not the shop. Two nullable text columns on ShopLocation, beside contactPhone and the scanner flags, edited in Settings → Stores. The shop-level paymentZaadEnabled / paymentEdahabEnabled toggles stay where they are and keep their meaning: the shop decides whether it takes ZAAD, each branch supplies which till receives it. buildReceiptFromSale already takes a location argument, so the plumbing is free.
  • Receipt branding is a plan module, default on. Set at platform level in the plan editor, not by the shop owner. Modelled as a new entry in MODULES (src/lib/entitlements.ts) that removes the footer when a plan grants it — so no plan granting it means every receipt carries the mark, which is the default we want. multi_currency and data_export are already non-screen capability modules, so there's precedent.

Still open

  • The reference is print-shaped. The in-app modal preview (receipt-modal.tsx) is React Native, not HTML — it has to be rebuilt by hand to match, including a monospace font that exists on both iOS and Android. Should the modal match, or only the printed, PDF and shared output? This is the larger half of the work.
  • Minor, follows from the QR: a laser wedge scanner can't read a 2D symbol, only an imager can. Locations with hardwareScannerEnabled would have to scan receipts on the camera instead. Worth confirming that's acceptable before the scan-to-return work starts.
