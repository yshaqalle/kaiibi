A scanner is a keyboard, so the OS takes the keyboard away

Plug an HID barcode scanner into a till and the operating system stops offering the on-screen keyboard — to it, a keyboard is already attached. Scanning works; typing stops. Staff can't name a product, set a price, or count a drawer. This is the OS's decision, not the app's, which is what makes it worth designing around rather than fixing in code.

Verified, not assumed

On an Android tablet show_ime_with_hard_keyboard is 0 by default. Flipping it to 1 with the same scanner attached brings the keyboard straight back (mInputShown=true). iOS has the same behaviour and no setting at all.

Part 1 — Android: name the cause, and put the switch one tap away

The app can detect the attached keyboard; it cannot flip the setting (that needs WRITE_SECURE_SETTINGS, which Play-installed apps do not get). So it says what is happening and hands over to the OS — the same shape as the camera-permission path, which already deep-links into Settings rather than pretending it can grant itself permission.

The honest limit of this part

It is Android-only, it is per-device, and it needs someone with the tablet in their hands. It does nothing for an iPad. That is why Part 3 exists.

Part 2 — stop the app adding to it

WedgeSink is an invisible, permanently-focused input; its own file states the rule that callers must unmount it while a modal is open "rather than leaving the two to fight." POS honours that for the camera scanner, the add-product modal and the receipt — and not for the register sheets, which auto-focus a text field the moment they open.

A few lines, and correct whatever happens with the rest: a field that asks for focus should never be competing with one that takes it back every 700ms.

Part 3 — iPad: the app brings its own keyboard to the forms

iOS offers no setting and no API. The only route is the one the search box already takes — the app draws the keyboard itself. This is the real fix, and the largest piece: it turns a single-purpose search keypad into something forms can use.

the whole point
Because the app's keypad never asks the OS for focus, the wedge keeps it: a barcode scanned halfway through typing a name still fills the barcode field. A system keyboard cannot do this — taking focus is exactly what breaks scanning.

Open questions this raises

QuestionProposed answer
Which fields get it? Only where a till actually types: the product form, the register sheets, the customer quick-add. Not Settings, not Accounting — those are done on a phone or a laptop, where no scanner is attached and the system keyboard works.
Where does the dock live? Bottom of the modal it belongs to, not the screen root — the search keypad docks at the screen root because the search row cannot reach it from inside the scroll flow; a form owns its own bottom edge.
Capital letters? Product names need them. That means a Shift the search keypad deliberately does not have — the first place this stops being the same component and becomes a bigger one.
When is it used? The same gate as today: only when a keyboard is confirmed attached (onScreenKeypad). A wrong true takes typing away from someone who had it.
