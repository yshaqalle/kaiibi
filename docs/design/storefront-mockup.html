Kaiibi · Storefront

A shop gets a real web address, with real products, that customers can actually order from.

xamdi.kaiibi.com renders the products already flagged is_listed_online, takes an order through a cart, and answers questions over WhatsApp. Customer pays on collection or delivery. Fulfilment and the tie into the books come next.

Cart buys. WhatsApp asks.

Two channels, two jobs. Add to cart is the primary action; "Ask about this" is for the question a photo can't answer.

No money online

Customer pays on collection or delivery. Stored per-shop as payment_mode so online payment is a later value, not a migration.

Form panel, not inline editing

Content is edited in a normal bento screen with a live preview. Click-anything editing is its own spec.

Three photo-optional themes

Every theme is designed to look deliberate with zero images. Most kaiibi shops will have few.

Why both, and why the cart is primary. An enquiry-only page puts the shop back where it started: a phone full of "is this available?" messages to answer by hand, one at a time, with no record. The cart is what turns that into a row someone can work. But a cart alone loses the sale where the customer needs to know whether the cord reaches the socket, or whether you have it in black — the questions that stop a purchase and that no product grid answers. So: cart for buying, WhatsApp for the thing that would otherwise be an abandoned page.

Accent on white 8.02:1

Presets, not a colour wheel. A free hex picker lets a shop owner put yellow text on a white page and publish it. Every palette here is four values checked against WCAG AA before it ships — the lowest is Saffron at 5.92:1 for accent-on-white, the same discipline theme.ts already applies to every app token.

A palette is four custom properties — ground, soft, ink, accent. Themes render through them, so three themes and six palettes is nine things to build and verify, not eighteen. Adding a seventh palette later is one line and a contrast check.

WhatsApp green is not themeable. The Message on WhatsApp button stays #1f7a4d in every palette. It's a recognised affordance — recolouring it to match a shop's accent costs the one thing that makes it get tapped.

Both place the order. WhatsApp also opens a chat with your basket already written out.

Both buttons create the same order row. This is the decision worth defending: a "checkout via WhatsApp" that only opens a chat produces sales the shop can't see in the app, can't count, and can't fulfil through the inbox — the exact fragmentation the storefront is meant to end. So the WhatsApp button writes the order first, then opens wa.me prefilled with the order number and every line. The shop gets a tracked row and a thread. If the customer never sends the message, the order still exists.

Area is a list the shop owns, not a map. Hargeisa addresses are landmarks, not street numbers, so a free-text address field produces things a rider can't use. A shop-configured area list plus a landmark line is what a delivery actually runs on. The area list lives in the storefront settings — see the admin screen — and if a shop lists none, the delivery option doesn't appear at all and checkout is collection-only.

Phone is required and normalised to E.164 — same treatment as the shop's own WhatsApp number. It is the only way the shop reaches this customer, and a mistyped one makes the order worthless.

A ledger is read down a column, so the table takes the full width and sits outside the grid — the strip above it is the part you glance at. That is the one decision the bento skill asks you to get right, and putting this table in a BentoCell span={7} would cost a nested sideways scroll on a phone.

Unconfirmed value is not revenue. The tile says "not counted as sales yet" because nothing here touches the ledger until an order is fulfilled. An order is a customer's intention; a sale is a thing that happened. Counting the first as the second would put money in your dashboard that no one ever paid.

Stock is checked at confirm time, not order time. Nothing is reserved when a customer adds to a cart, so the shortfall surfaces here — with a wrong caveat that names the fix, because the shop can still rescue the sale with a phone call.

i Nothing is in your books yet. Marking this Delivered records the sale, takes the stock, and posts to the ledger — goods to 4000, the delivery charge to 4300.

One state change writes to the books, and it is the last one. Placed, Confirmed and Ready are shop workflow and touch nothing. Delivered (or Collected) is what creates the sale, moves stock, and posts the journal entry — through the same post_complete_sale path the register already uses, so an online order and a counter sale land in the ledger identically.

Cancel is not a refund. No money moved and no stock left, so cancelling before fulfilment writes nothing to the ledger — it just closes the order. Only an order already marked delivered can be refunded, and that is the existing refund path, not a new one.

A draft shop and a nonexistent shop render the same page. If "not published yet" were distinguishable from "no such shop", the subdomain becomes an oracle: anyone could walk names and learn which shops are on kaiibi and what they're called before they open. One page, one message, no leak. It also means the public read path never sees an unpublished row — enforced in RLS, not in the client.

What this costs in schema

Small. Nothing existing changes shape.

ChangeWhy
shops.slugGlobally unique, nullable until set. Reserved list blocks www, app, api, admin, platform.
storefrontsOne row per shop: theme, palette, headline, about, hero image, offers_delivery, payment_mode, published_at. Theme and palette are CHECK-constrained to the shipped catalogues — an unknown value must fall back to the default rather than render an unstyled page. Separate table so the public read path can be granted on it alone.
shops.whatsapp_e164contact_phone is free text and can't be dialled. A link needs E.164. Required to publish, not to exist.
storefront_delivery_areasName plus fee_cents per area, ordered. A child table rather than JSON so a fee is a typed column that can be summed and checked >= 0. A flat fee is just the case where every row carries the same number, so one structure covers both.
ordersPer-shop sequential number, customer name and E.164 phone, fulfilment (collect / deliver), area, landmark, note, payment_mode copied at creation, status, subtotal_cents, delivery_fee_cents and total — the fee copied at order time, like every line price, so raising the charge next month never rewrites what a customer already agreed to. No customer account, no auth — the phone number is the identity.
order_itemsProduct reference plus name, unit price and quantity captured at order time. An order must still read correctly after the product is renamed, repriced or deleted — the same reason your sale lines don't join live to products.
Anon insert on ordersAn unauthenticated write, which nothing in this app has today. Needs a rate limit and a server-side recompute of every line total — a client-supplied price is a discount anyone can grant themselves.
Module storefront14th entry in entitlements.ts, gated in DB write policies and the client route guard, as the file's header requires.
Anon read policyThe one genuinely new security surface: unauthenticated select on published storefronts and their is_listed_online products, exposing name, price, stock and image only — never cost.

The delivery fee needs an account that doesn't exist yet. The chart of accounts (20260904000100) has 4000 Sales Revenue, 4100 Sales Returns and 4200 Discounts Given — nothing for delivery. Posting the fee into 4000 inflates goods revenue with income that carries no cost of sales, and quietly flatters gross margin on every report you just built. It wants its own 4300 Delivery Income, seeded the same way the others are. That lands in the fulfilment spec, when an order becomes a sale — but the column has to be separate from day one or the number is unrecoverable later.

The one that needs care. Every other table in this app is read by an authenticated member of one shop. This adds a path with no session at all, and the column list is the whole defence — products.cost_cents sitting one column away from price_cents is the thing a careless select * leaks. The public read goes through a view or an explicit column list, and a test asserts cost is absent.

Deliberately not in spec 1

Left outWhere it goes
Click-anything inline editingIts own spec, over this same content model. The button and its position are already right.

Customer accounts, order tracking pageNot scheduled. A number and a phone call. A signup wall in front of checkout would cost more orders than tracking wins.

The honest scope warning. This is four subsystems in one spec: a public storefront, an editor, an ordering system, and a fulfilment workflow. It is large. It is also the smallest thing that is actually useful — a page nobody can order from, or orders nobody can work, is not a shippable half. The plan below phases it so each phase leaves the tree working, and the phase boundaries are where you can stop if it turns out to be too much at once.
