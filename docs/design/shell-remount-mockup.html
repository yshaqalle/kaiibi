Web shell · admin-tabs.web.tsx

Crossing 820px doesn’t resize the screen — it destroys it

The web shell returns two structurally different trees either side of TABLET_BREAKPOINT, and each one contains its own <Slot />. So dragging the window past 820px doesn’t reflow Inventory. It unmounts it and builds a new one — which is why a scanned product vanished out of a search box that had just found it.

The proposal, in one line

One root, one <Slot />, at a position that doesn’t move. The rail, the header and the bottom nav switch around it — the screen itself is never rebuilt.

What happens today

Scan 8809447255972 on a narrow window and Inventory does its job: the code fills the box, the result bar names the product, the list narrows to it. Widen the window past 820px and all three are gone — not hidden, gone, because the component that held them no longer exists.

the bug Empty box, no result bar, all 86 products back. The banner survived because it lives in the shell, above the <Slot /> — which is the tell.

Why — the two trees

React keeps a component alive by position. Same type in the same slot: it updates. Different type, or a different parent chain: it tears the old one down and mounts a new one, and every useState inside goes with it. Today the routed screen sits at a different address on each side of the breakpoint.

width < 820

  • View mobileRoot
    • View mobileHeader
    • View bannerSlot
    • View mobileSlot
      • <Slot />Inventory lives here
    • View bottomNav

width ≥ 820

  • AdminSidebar
    • View tabs
      • View sidebar
      • View slot
        • View topBar
        • View bannerSlot
        • <Slot />…and here instead

Two different roots — View against AdminSidebar — so React discards the whole left-hand tree and builds the right-hand one from nothing. Nothing inside can survive that, because nothing inside is the same object afterwards.

width < 820

  • View rootcolumn
    • nullno rail
    • View slot
      • View headermobile
      • View bannerSlot
      • <Slot />same address
    • View bottomNav

width ≥ 820

  • View rootrow
    • View sidebarthe rail
    • View slot
      • View headertop bar
      • View bannerSlot
      • <Slot />same address
    • nullno bottom nav

Same root type, same child indices, same parent chain down to the screen. The rail appears and the bottom nav disappears — those are chrome and may be rebuilt freely — but <Slot /> never changes address, so Inventory is updated rather than replaced. The root’s flexDirection flips row to column; that is a style, not a new element.

What it changes on screen

Nothing. That is the point, and the thing worth checking before it ships: both layouts must come out pixel-identical to the two frames at the top of this page. The whole gain is invisible — it is what doesn’t get thrown away.

The last row is the honest limit. A tab switch genuinely swaps which route <Slot /> renders, so the old screen must unmount — no tree shape prevents that. Only the session store covers it. The two fixes overlap; neither replaces the other.

Verdict

What gains

  • Resizing and iPad rotation stop wiping the screen — filter, sort, scroll and open modals all survive.
  • One shell instead of two: today the mobile branch carries its own menu sheet, support sheet and logo upload, duplicating AdminSidebar’s.
  • The duplicated logo upload in the mobile branch is the stale copy — it never picked up useShopLogo().

What is neutral

  • Every pixel. Both layouts keep their current chrome, spacing and nav treatment.
  • Native is untouched — admin-tabs.tsx keys on device class, not width, and never crosses a branch while mounted.
  • Tab switching behaves exactly as it does today.

What the shape costs

  • ~200 lines moved across the two files that render every admin screen on web. A structural edit, not a local one.
  • The bottom nav uses emoji icons and the rail uses image assets. Merging the shells without merging those lists means two nav definitions in one file.
  • It needs eyes on both widths. Tests can prove the screen survives the breakpoint; they cannot prove the rail still looks right.
