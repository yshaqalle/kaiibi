Scanner · Search · Touch

One till, three ways in

A shop runs on whatever devices it has. A couple of phones, a tablet on the counter, maybe one till with a barcode scanner wired to it. Scanning is the fast path on that one device — it must never become the price the other twenty pay, and it must never take typing away from the device that has it.

The rule this is built on

Search and touch always work, on every device, whatever else is attached. If a scanner happens to be there, it is added on top — never traded against.

Why this needs designing at all

A barcode scanner in HID mode is a keyboard as far as the operating system is concerned, and iOS hides the on-screen keyboard the moment a keyboard is attached. So the one device that scans is also the one device where tapping the search box gives you a blinking cursor and nothing to type with. There is no public API to override that — the fix has to be ours, on our side of the glass.

The second half is quieter. To catch scans, the app keeps an invisible focused field alive. Anything else that wants the keyboard has to win it back — which is a fight, and the field the cashier actually tapped should never be in one. Owning the text ourselves ends the fight: the search box stops needing focus at all, so the scanner keeps it permanently and both work at the same time instead of taking turns.

The two worlds

One switch decides which of these a device gets, and it is answered per device, not per store: is a keyboard actually attached right now? Most tablets and phones are on the left and never change. Only the till with the scanner is on the right.

Kaiibi keypadours

The keypad writes into the same search text the field already uses, so the field never takes focus and the scanner never loses it. Scanner ready is not decoration: it is the promise that scanning a barcode right now still works, mid-word.

Which keypad

This is the decision I would like judged. Both cover the same keys — letters, digits, space, delete — because product names and barcodes both get typed here. They differ only in how a hand finds a letter.

Shown abovetap to compare

QWERTY34px keys

QWERTY

The layout every phone in the shop already uses, so muscle memory carries over and nobody is learning a second alphabet. Keys land near 30px on a phone — under the 44px touch target, which is survivable for search and would not be for a keypad that took money.

A–Z

Findable without keyboard literacy: a letter is where the alphabet says it is. Seven columns give slightly bigger keys. The cost is that anyone fluent on a phone keyboard gets slower, and this is the till — speed at the counter is the point.

Not building: a full keyboard

No shift, symbols, emoji, autocorrect, predictive bar or language switching. Product search is case-insensitive and matches on name, SKU and barcode, so every one of those would be weight with nothing on the other end.

The third row is the safety valve, and it is deliberately narrow: it fires only when the platform cannot answer at all, so a shop that scans happily today can never be silently switched off by a gap in detection. The store setting stops meaning there is a scanner here and starts meaning this store uses scanners — permission, with the per-device truth measured rather than declared.

Still open

Does the keypad open on tap, or sit there?

Drawn here as open on tap, matching what a keyboard does. Always-visible would cost roughly a third of the screen on a phone permanently, on the one device where the product grid matters most.

POS as well as Inventory?

Both screens have the same search row and the same wedge, so the same treatment applies to both. POS is where the speed argument bites hardest.
