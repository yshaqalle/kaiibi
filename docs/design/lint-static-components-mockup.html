1 · Why static-components is the one that actually costs something

This is not a style rule. A component's identity is what React uses to decide between updating a subtree and throwing it away.

Where it bites. These are the Inventory and Customers list headers. The parent re-renders on every keystroke in the search box and on every sort — and each time, seven header cells are destroyed and rebuilt rather than re-rendered. The cells hold no state, so nothing breaks; it is pure churn in exactly the screens that render the most rows.

The change, in customer-table-row.tsx

Before

    </Pressable>
  );

  return (
    <View style={styles.headerRow}>
      <View style={styles.dataCols}>
        <HeaderCell field="name" label="NAME" style={colName} />
        …
After
// Module scope: ONE component type for the life of the module, so a
// re-render updates these cells instead of rebuilding them.
function HeaderCell({ label, style, active, direction, onPress }: {
  label: string; style: object; active: boolean;
  direction: SortDirection; onPress: () => void;
}) {
  return (
    <Pressable onPress={onPress} style={[styles.headerCell, style]}>
      <Text style={styles.headerLabel}>{label}</Text>
      {active && <Text style={styles.sortArrow}>{direction === 'asc' ? '▲' : '▼'}</Text>}
    </Pressable>
  );
}

export function CustomerTableHeader({ sortField, sortDirection, onSort }) {
  return (
    <View style={styles.headerRow}>
      <View style={styles.dataCols}>
        <HeaderCell label="NAME" style={colName} direction={sortDirection}
          active={sortField === 'name'} onPress={() => onSort('name')} />
        …

Why active and onPress rather than passing field and onSort through: hoisting the component means it can no longer close over sortField. Passing the answer (“are you the sorted column?”) instead of the inputs keeps the call site readable and drops the SortField generic from a component that only ever draws a label and an arrow.

product-table-row.tsx takes the identical change — same component, same five call sites plus two — which is where 5 of the 8 errors live.

2 · One shared cell, or one per file?

The two HeaderCells are character-for-character identical. Their styles are not quite.

OptionWhat it doesCost
A — hoist in place recommended Each file keeps its own HeaderCell, moved to module scope. Kills all 8 errors. Zero visual change. One duplicated 10-line component.
B — one shared component Extract SortableHeaderCell for both screens. Kills the 8 and the duplication. The two files style the label differently — see below. Unifying them is a real, if tiny, visual change. 
// customer-table-row.tsx
headerLabel: { fontSize: 10, fontWeight: '900', color: '#555555', letterSpacing: 0.6 },   ← a hex literal
// product-table-row.tsx
headerLabel: { fontSize: 10, fontWeight: '900', color: theme.bentoMuted, letterSpacing: 0.6 },
A separate finding, worth logging either way. customer-table-row.tsx writes #555555 straight into a screen, which the bento rules forbid — colours come from Colors.light tokens. The nearest token, bentoMuted, is #5e5d65: a shade warmer and marginally lighter. Swapping it is almost certainly right, but it is a pixel change to the Customers header, so it belongs in a commit that says so rather than smuggled inside a lint fix.

Recommendation: take A now. It is provably behaviour- preserving — the same JSX, moved — which is what you want in a change nobody is going to eyeball. B and the hex-literal fix are a better end state and should follow as their own small PR, where “the Customers header changed colour by one shade” is the visible headline rather than a footnote.

3 · The apostrophe

One character, in product-form.tsx.

Before
<Text style={styles.toggleHint}>
  Show this product in the online Discover feed once it's live.
</Text>
After
<Text style={styles.toggleHint}>
  Show this product in the online Discover feed once it&apos;s live.
</Text>

JSX decodes the entity at build time, so the rendered string is unchanged — and &apos; is already the house style: shop-drawer.tsx and platform-overview.tsx both use it.

4 · What this proposal deliberately does not touch

pos.tsx — refs and purity (9 errors)

// Assigned during render rather than in an effect: an effect would run after
// a first paint that had already priced the line with a different clock.
const pricedAtRef = useRef<number | null>(null);
if (cart.length === 0) pricedAtRef.current = null;
else if (pricedAtRef.current === null) pricedAtRef.current = Date.now();

The linter is not wrong — under concurrent rendering a render can be discarded and replayed, and this would keep a stale clock. But the author knew exactly what they were doing, wrote down why, and the naive “fix” (move it into an effect) reintroduces the mispricing bug the comment exists to prevent. This needs whoever owns pricing, deliberately, with a test that pins the behaviour first. Not a lint cleanup.

set-state-in-effect (34 errors, 27 files)

The dominant class and the least urgent: almost all are “load on mount, then setState”, which costs one extra render pass and breaks nothing. Worth a sweep one day, file by file, in a PR whose entire job is that. Folding 27 files into any feature branch makes the feature unreviewable.

category-donut-chart.tsx — immutability (1)

A running percentage mutated inside .map. Correct today, because the callback runs synchronously during render; the compiler simply cannot prove it. The non-mutating rewrite is a prefix-sum and is slightly harder to read than what is there, so it earns its place only in a dedicated pass.

  1. Hoist HeaderCell in customer-table-row.tsx and product-table-row.tsx, converting the seven call sites to active / onPress.
  2. Escape the apostrophe in product-form.tsx.

Net effect: 9 of 54 errors gone, two of the busiest list screens stop rebuilding their headers on every keystroke, and no pixel moves. The other 45 stay visible and documented rather than suppressed — nothing gets an eslint-disable in this proposal.
