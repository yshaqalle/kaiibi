Kaiibi · Help & support · what the final review found

Six gaps, drawn

The feature works and nothing here blocks a merge. These are the things the whole-branch review caught that no single task could see — shown as what actually happens on screen, rather than described.

1 · Deleting a person can widen who reads their thread The one that matters

This is the only gap that touches the privacy guarantee. It is not reachable from inside the app — but it is reachable from the Supabase dashboard, which is where someone tidying up old accounts would be.

3 · The thread changes meaning

Your ZAAD payment cleared
KB-2484 · Billing · addressed to nobody
Amina · gone—
Yusuf · Manager · has Settings accessNOW READS IT
Hodan · Cashierstill cannot
⚠A message meant for one person is now readable by everyone who can reach Settings. The promise the composer made is no longer true, and nobody was told.

Why it happens. The rule never stored who this is for as a fact. It works it out by asking “is the addressee field empty?” — treating empty as “this one is for the whole store”. So the moment the field empties for an unrelated reason, the answer to a privacy question changes with it.

-- today: scope is GUESSED from a field that can empty on its own where opened_by = 'platform' and addressed_user_id is null -- ← "must mean the whole store" and has_shop_permission(shop_id, 'settings.access') -- proposed: scope is STORED, and says what it means where opened_by = 'platform' and addressed_scope = 'store' -- ← set once, when the thread is opened and has_shop_permission(shop_id, 'settings.access')
The fix, and why this shape

Add an addressed_scope column holding 'store' or 'person', set when the thread is opened, and key the rule on that. Then deleting the addressee leaves a thread nobody can read — which is the safe way to fail — instead of one everybody can. One migration, plus a check in verify-support.sql that deletes the addressee and asserts a Settings-access holder still reads zero rows.

2 · “Email” is a choice nothing can act on Broken promise

The store is offered three ways to be replied to. Two of them work.

What the store is told

Reply to me on
● In the app ○ WhatsApp ◉ Email

Picking WhatsApp doesn’t change where the reply is written — it tells us to nudge you there too.

ⓘThe same sentence covers Email. A shop owner reasonably reads this as “they’ll email me.”

What the operator sees

Paid on ZAAD but still showing as unpaid
KB-2481 · Hooyo Grocery · Amina Hassan
Needs a reply Billing no WhatsApp chip — they didn’t ask for it
Who this is
Store Hooyo Grocery
Person Amina Hassan
WhatsApp —
Email not shown anywhere
⚠The operator has no way to know they asked for email, and no email address to send to — the console is deliberately not allowed to read one.
The fix: remove the option

In-app is the default and always works; WhatsApp has a real one-click hand-off. Email is a third choice that changes nothing and quietly promises something. Deleting the chip is honest and takes minutes. Keeping it would mean widening what the console can read about a person, adding a chip, a rail row and a mailto: hand-off — real work, for the channel these shops read least.

3 · Attachments only go one way, on one message Scope gap

Four places in the conversation could carry a file. One of them can.

CAN Store — the first messagethe compose form picker ✓
CANNOT Store — every reply after thatsupport-thread-view.tsx has no picker no picker
CANNOT Operator — replyingthe reply panel no picker
CANNOT Operator — starting a conversationthe outbound composer no picker
⚠Everyone can open an attachment. Only the very first message can carry one. So a store that forgets a screenshot, or is asked for one, cannot send it — and we can never send them a receipt or a document.

This is also what made the blocker a blocker: the failure message used to say “open the conversation and try again”, pointing at a reply box with no picker. That copy is fixed, but the underlying limit is still here.

The fix: three small pieces, already half-built

The AttachmentPicker component exists and the storage rules already allow it — the path is keyed on the thread, not on who is writing. What is missing is wiring it into the store’s reply box, adding an attachment payload to the two operator actions, and putting the picker on the two console surfaces. Schedule it rather than squeeze it in.

5 · The console has no unread mark Needs a prerequisite

The store gets a badge on its ☰ when we write. We get nothing when a store writes.

The store's side — built

☰
⚙ Settings
✉ Help & support 2

The console — missing

OverviewStores Requests 2 Support PlansAudit log
⚠Requests has a count. Support does not. An operator on any other tab has no signal that a store is waiting.

Why it can’t just be switched on. A badge needs to know what you have already looked at, and nothing currently records that an operator opened a thread — only that they replied to one. So the count has nothing to subtract.

The fix, and a question worth asking first

Add a “mark read” action called when the reply panel opens, then the badge is simply the threads a store wrote last that you haven’t opened. But the queue already sorts by whose move it is, so anything waiting on you is at the top of the list the moment you open the tab. Worth deciding whether the badge earns its build.

6 · Three places the spec is wrong, not the code Amend the document

The rail should show role and email
The console is deliberately forbidden from reading a shop’s staff list — a security test asserts it. The spec asked for something the design rules out. fix the spec
KPI: median first reply
Nothing records when a thread was first answered, so there is no figure to compute. Either add the timestamp deliberately or drop the tile. decide
“Preview as the store”
A genuine unbuilt control. Cheap to add, low value — an operator writing one paragraph rarely needs to see it framed. build or cut

What I’d do, in order

  1. One migration for the privacy seam. The addressed_scope column, the rule keyed on it, a test that deletes the addressee and proves nobody inherits the thread. Roll in the one function still missing its search-path pin while the file is open.
  2. Delete the Email chip. Minutes, and it stops the app promising something it cannot do.
  3. Add the operator chips to the filter row. Ten minutes.
  4. Attachments both ways, as its own scheduled piece — the picker exists, the storage rules already permit it, so it is wiring rather than design.
  5. Decide on the console badge before building it; the sort may already cover the need.
  6. Amend the spec for the three items above where the document, not the code, is what is wrong.

Items 1–3 are one sitting and clear everything security-shaped. Nothing on this page blocks a merge today.
