Exporting a report

Every report screen in the app is a table you can read and cannot take away. The export machinery already exists and is used on six other screens — this is about pointing it at the reports, and the three decisions that are not obvious once you do.

1 · The gap

Nothing here is new infrastructure. ExportMenu, rowsToCsv, buildTableReportHtml, buildDashboardReportHtml, shareCsv and sharePdf all ship. Six screens call them; the reports are not among those six.

So the legacy statements screen is the odd one out in both directions: it is the only screen with a PDF and no CSV, and the only report that exports at all. Whatever lands here should fold it back into the same pattern rather than leaving a second one.

2 · Where the control goes

On the title row, via useHeaderActions — the mechanism that exists precisely for this, and whose own comment says so: "Export needs that tab's filtered rows". It travels upward because the shell renders the header before the tab, and moving the title down into the tab would take the range selector with it and reset the range on every switch.

The buttons are chips, not the cream block

ExportMenu hardcodes #111111, a 10px radius and 11px text — the cream palette, from before Accounting was converted. It already renders that way on four bento screens, which is the known interim state, but a fifth and sixth placement is the moment to give it a bento variant rather than widen the debt. It also sits in the control-bar row here, beside the range and store chips, so it should be shaped like them.

Quiet chips rather than a solid fill, on the rule the hub cards already follow: solid means the press writes. An export produces a file and changes nothing in the shop, so it takes the same weight as the range picker it sits beside.

3 · Decision one — where the CSV columns come from

This is the real work, and the reason it is not a one-line change per screen. The report tables and the exporter do not speak the same type.

// what the report screens have — components, for the screen
type Column<T>    = { key: string; header: string; numeric?: boolean; render: (row: T) => ReactNode }

// what the exporter needs — text, for a file
type CsvColumn<T> = { header: string; value: (row: T) => string }

render returns a <ValueCell> element. There is no honest way to get "$904.00" back out of a React element, so the text has to be declared somewhere. Two places it could go:

Option A · the precedent

A second column list per screen

Exactly what Inventory, People and Expenses already do — PRODUCT_EXPORT_COLUMNS beside the display columns. Six screens set this precedent, so it needs no argument to justify.

const COLUMNS: Column<Row>[] = [
  { key:'cat', header:'Category',
    render: r => <NameCell text={r.name}/> },
]
const EXPORT_COLUMNS: CsvColumn<Row>[] = [
  { header:'Category',
    value: r => r.name },
]

The cost: two lists per screen across seven screens, and nothing makes them agree. Rename a column header and the CSV keeps the old one silently.

Option B · recommended

One list, with the text on it

Add an optional text to Column<T>. DataTable ignores it; the exporter reads it. One list is the source of both, so they cannot drift.

const COLUMNS: Column<Row>[] = [
  { key:'cat', header:'Category',
    render: r => <NameCell text={r.name}/>,
    text: r => r.name },
]

// and one helper, once:
csvColumnsOf(COLUMNS) // drops any column
                     // with no `text`

A column with no text is simply not exported — which is the right default for an actions column or a sparkline, and makes "is this in the file?" a visible property of the column rather than a second list to remember.

Recommending B, with one caveat worth stating plainly: it is the option that does not match the six existing screens, so it either leaves two patterns in the app or implies a follow-up to move those six across. I would take that trade — the drift Option A allows is the exact failure this codebase keeps writing comments about, and the six existing callers can move later without a behaviour change. If you would rather stay uniform today, A is a defensible call and the rest of this document is unaffected.

4 · Decision two — the reports that are not one table

A PDF can hold sections. A CSV file is one grid. Two of these reports have more than one table, so the two formats cannot carry the same thing and the screen has to say which it is giving you.

5 · Decision three — what the subtitle promises

Every exported file carries a subtitle line, and it is the only place the file records what it is a view of. Get it wrong and a spreadsheet outlives the context that made it true.

Four of the seven reports follow the shell's date range; three do not, and each already declares which on its hub card via followsRange. The export subtitle must read that same flag rather than printing the range unconditionally — a Low Stock export stamped "1–14 Aug" would be a file claiming to be a fortnight's stock position, which is not a thing that exists.

ReportFollows the rangeSubtitle on the file
Sales Reports, Item Performance, Sales by Employee, Sales by Category, Stock MovementYes1–14 Aug 2026 · All stores
Inventory Balance, Low Stock & ReorderNoAs at 14 Aug 2026, 4:32 PM · All stores — an instant, with the time, because stock moves during a day

The store filter goes on every file for the same reason: an inventory export from one shop of three, opened a month later, is indistinguishable from the whole company's unless it says so.

6 · Scope

  • The seven report screens get Export CSV and Export PDF on the title row. That is the request, and it is the bulk of the work.
  • Fold the legacy statements screen in. It has a PDF and no CSV, and its own bespoke header button. Moving it onto the shared control gives it a CSV and removes the second pattern.
  • Give ExportMenu a bento variant rather than placing the cream block on two more converted screens.
  • Not in this pass: the ledger screens. Trial Balance, Journals, Chart of Accounts, Audit Log and Fixed Assets are tables and would be easy; the three statements are StatementRow lists with sections and subtotals, which is a different export shape and a different conversation about whether a balance sheet as a CSV is a useful object at all. Worth doing, worth doing separately.

One thing I would flag before building: decision one is the only one that is hard to undo. Adding text to Column<T> touches a type every table in the app uses, so it is worth agreeing before rather than after.
